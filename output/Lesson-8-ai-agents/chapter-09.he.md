# LangChain - מסגרת עבודה לבניית אפליקציות LLM

## למה בכלל צריך Framework כמו LangChain

אחרי שהבנו מהו Agent, מהם Tools, מהו Memory, ומהם דפוסי העבודה המרכזיים לבניית מערכות Agentic, עולה שאלה מעשית: איך מחברים את כל הרכיבים האלה בקוד בצורה מסודרת?

אפשר כמובן לבנות הכול לבד. אפשר לכתוב קוד Python שקורא ישירות ל-API של מודל, לבנות Prompt ידנית, לחבר פונקציות ככלים, לשמור היסטוריית שיחה, לשלוף מידע ממסמכים, ולנהל את כל שלבי העבודה בעצמנו.

אבל ככל שהמערכת גדלה, מתחילים להופיע חיבורים שחוזרים על עצמם שוב ושוב:

```bash
Prompt → Model → Output Parser

User question → Retriever → Context → LLM

Agent → Tool → Tool result → Final answer

Conversation history → Prompt → Model response
```

במקום שכל פרויקט יגדיר מחדש את כל החיבורים האלה, נוח להשתמש ב-Framework שנותן מבנה וכלים מוכנים. כאן נכנס LangChain.

LangChain הוא framework לבניית אפליקציות שמבוססות על LLMs. הוא לא מחליף את המודל עצמו, אלא מספק שכבת עבודה סביבו: דרך להגדיר Prompts, לחבר מודלים, להשתמש בכלים, לעבוד עם זיכרון, לשלוף מידע ממסמכים, ולבנות תהליכים שמורכבים מכמה שלבים.

במילים פשוטות, LangChain עוזר להפוך שימוש ב-LLM מקריאה בודדת למודל, למערכת שמורכבת מרכיבים שמדברים זה עם זה בצורה מסודרת.

זה חשוב במיוחד כאשר עוברים מצ’אט פשוט למערכת אמיתית. בצ’אט פשוט אפשר לשלוח שאלה ולקבל תשובה. אבל במערכת RAG או Agent יש בדרך כלל כמה שלבים: להבין את השאלה, לשלוף מידע, לבנות Prompt עם context, לקרוא למודל, לפרש את התוצאה, ואולי להפעיל כלי נוסף.

LangChain נותן דרך לארגן את השלבים האלה בצורה מודולרית יותר, כך שכל רכיב במערכת מקבל תפקיד ברור ואפשר להחליף, לבדוק או להרחיב אותו בלי לבנות את כל המערכת מחדש.

## הרכיבים המרכזיים ב-LangChain

כדי להבין את LangChain, כדאי לראות אותו כאוסף של רכיבים שמיועדים להתחבר זה לזה. כל רכיב אחראי על חלק אחר במערכת, והחיבור ביניהם מאפשר לבנות תהליכים מורכבים יותר מקריאה פשוטה ל-LLM.

הרכיבים המרכזיים הם:

<div dir="rtl">

| **רכי**ב | **תפקיד** |
| --- | --- |
| **Prompt Templates** | תבניות Prompt שמאפשרות לבנות הנחיות בצורה מסודרת ודינמית |
| **Models** | חיבור למודלי שפה שונים, בענן או מקומית |
| **Output Parsers** | רכיבים שממירים את תשובת המודל לפורמט נוח יותר, למשל טקסט נקי, JSON או מבנה נתונים |
| **Chains** | רצף של שלבים שמחברים Prompt, Model, Parser ורכיבים נוספים |
| **Tools** | פונקציות או שירותים חיצוניים שה-Agent יכול להפעיל |
| **Agents** | רכיבים שמסוגלים לבחור פעולה או כלי לפי המשימה |
| **Memory** | מנגנון לשמירה או שליפה של הקשר משיחה או ממקור חיצוני |
| **Retrievers** | רכיבים שמחזירים מידע רלוונטי ממסמכים, Vector DB או מקור ידע אחר |

</div>

לדוגמה, במערכת RAG פשוטה נשתמש בכמה רכיבים יחד:

```bash
Prompt Template
+
Retriever
+
Model
+
Output Parser
```

ה-Retriever מחזיר את הקטעים הרלוונטיים מהמסמכים, ה-Prompt Template משלב את השאלה עם ה-context, המודל מייצר תשובה, וה-Output Parser מחזיר את התוצאה בצורה נקייה וברורה.

ב-Agent עם Tools, המבנה יהיה מעט שונה. שם נרצה שהמערכת תדע אילו כלים קיימים, מה כל כלי עושה, ומתי כדאי להשתמש בו. במקרה כזה LangChain יכול לעזור להגדיר את הכלים, לחבר אותם ל-Agent, ולנהל את התוצאה שחוזרת מהם.

הנקודה החשובה היא ש-LangChain לא מוסיף “קסם” למודל. הוא בעיקר נותן דרך מסודרת לחבר רכיבים. ככל שמבינים טוב יותר את התפקיד של כל רכיב, כך קל יותר לבנות מערכת ברורה, לבדוק אותה, ולהחליף חלקים בלי לשבור את כל המבנה.

## LCEL - LangChain Expression Language

אחרי שמכירים את הרכיבים המרכזיים ב-LangChain, חשוב להבין איך מחברים אותם בפועל לתהליך עבודה אחד. כאן נכנס LCEL, כלומר LangChain Expression Language.

LCEL היא דרך דקלרטיבית להרכיב Chains. במקום לכתוב הרבה קוד שמפעיל כל שלב בנפרד, אפשר לחבר רכיבים בצורה קריאה וברורה, כך שכל רכיב מקבל קלט, מעבד אותו, ומעביר את התוצאה לרכיב הבא.

הדוגמה הבסיסית נראית כך:

```python
chain = prompt | model | parser
```

המשמעות היא:

```bash
Prompt
↓
Model
↓
Parser
```

ה-Prompt בונה את ההנחיה למודל, ה-Model מחזיר תשובה, וה-Parser מעבד את הפלט לפורמט הרצוי.

אחד הרעיונות המרכזיים ב-LCEL הוא שכל רכיב כזה מתנהג כמו Runnable. כלומר, אפשר להריץ אותו בממשק אחיד. לדוגמה:

```python
response = chain.invoke({"topic": "AI Agents"})
```

במקרה הזה אנחנו שולחים קלט ל-chain, וכל השלבים רצים לפי הסדר שהוגדר.

מעבר ל-invoke, קיימות גם צורות הרצה נוספות:

<div dir="rtl">

| **פעול**ה | **משמעות** |
| --- | --- |
| **invoke** | הרצה רגילה של chain על קלט אחד |
| **ainvoke** | הרצה אסינכרונית |
| **stream** | החזרת תשובה בהזרמה, חלק אחרי חלק |
| **batch** | הרצה על כמה קלטים יחד |

</div>

היתרון של LCEL הוא שהקוד הופך להיות קריא ומודולרי יותר. קל לראות אילו רכיבים משתתפים בתהליך, באיזה סדר הם פועלים, ואיפה אפשר להחליף רכיב אחד ברכיב אחר.

לדוגמה, אפשר להתחיל עם מודל אחד ובהמשך להחליף אותו במודל אחר, בלי לשנות את כל מבנה ה-chain. אפשר גם להחליף Parser, לשנות Prompt, או להוסיף שלב נוסף בתהליך.

במילים פשוטות, LCEL נותנת דרך נקייה לחבר רכיבים כמו Prompt, Model, Retriever ו-Parser לתהליך עבודה אחד. היא לא משנה את הרעיון הארכיטקטוני, אלא עוזרת לכתוב אותו בקוד בצורה מסודרת וברורה יותר.

## האם כדאי להשתמש ב-LangChain?

LangChain הוא כלי שימושי, אבל הוא לא תמיד הבחירה הנכונה לכל פרויקט. חשוב להבין מתי הוא באמת מוסיף ערך, ומתי עדיף להשתמש בקוד פשוט יותר.

LangChain מתאים במיוחד כאשר בונים מערכת שיש בה כמה רכיבים שצריכים לעבוד יחד: Prompt, מודל, Retriever, Memory, Tools ו-Output Parser. במקרים כאלה הוא נותן מבנה מוכן, מקצר זמן פיתוח, ומאפשר להרכיב תהליכים מורכבים בצורה מודולרית.

לדוגמה, אם בונים מערכת RAG, LangChain יכול לעזור לחבר בין שליפת המסמכים, בניית ה-Prompt, הקריאה למודל ועיבוד התשובה. אם בונים Agent עם Tools, הוא יכול לעזור להגדיר כלים ולנהל את האינטראקציה בין המודל לבין הכלים.

מצד שני, LangChain מוסיף שכבת abstraction. לפעמים השכבה הזאת מקלה על הפיתוח, אבל לפעמים היא גם מסתירה מה באמת קורה מאחורי הקלעים. אם המערכת פשוטה מאוד, למשל קריאה אחת ל-LLM עם Prompt קבוע, ייתכן שקוד Python רגיל וקריאה ישירה ל-API יהיו ברורים ופשוטים יותר.

**אפשר לחשוב על זה כך:**

כדאי להשתמש ב-LangChain כאשר:

- במערכת יש כמה רכיבי LLM שצריכים לעבוד יחד.

- צריך לשלב RAG, Tools, Memory או Chains.

- רוצים להגיע מהר לאב טיפוס עובד.

- רוצים לעבוד עם רכיבים מודולריים שאפשר לחבר ולהחליף.

כדאי להשתמש ב-Custom Python כאשר:

- התהליך פשוט וקצר.

- רוצים שליטה מלאה בכל שלב.

- רוצים לצמצם תלות בספריות חיצוניות.

- רוצים שקיפות מלאה לגבי מה שקורה בקוד.

ההחלטה אינה “LangChain טוב” או “LangChain רע”. זו החלטה ארכיטקטונית. אם LangChain מקצר את הפיתוח ומארגן את המערכת בלי להסתיר יותר מדי, הוא יכול להיות בחירה טובה. אם הוא מוסיף מורכבות מיותרת, עדיף להתחיל מקוד פשוט יותר.

כדאי להשתמש ב-LangChain כאשר הוא עוזר לבנות מערכת ברורה ומהירה יותר. לא כדאי להשתמש בו רק כי הוא פופולרי או כי הוא מופיע בדוגמאות. קודם צריך להבין את הבעיה, ואז לבחור את הכלי המתאים.

בסופו של דבר, LangChain הוא לא המטרה של המערכת, אלא אמצעי לבנות אותה בצורה מסודרת יותר. הוא עוזר לחבר בין Prompt, Model, Tools, Memory, Retrievers ו-Chains, אבל הוא לא מחליף הבנה ארכיטקטונית.

כדי להשתמש בו נכון, צריך קודם להבין מה המערכת צריכה לעשות: האם היא רק עונה על שאלה, האם היא שולפת מידע ממסמכים, האם היא מפעילה כלי, האם היא מנהלת Workflow, או האם היא צריכה לקבל החלטות בזמן ריצה.

רק אחרי שמבינים את סוג המערכת שרוצים לבנות, אפשר לבחור האם להשתמש ב-LangChain, באיזה רכיבים להשתמש, ואיפה עדיף לכתוב קוד מותאם אישית.

העיקרון החשוב הוא לא להתחיל מהספרייה, אלא מהבעיה. קודם מגדירים את מבנה המערכת, אחר כך בוחרים את הכלים שיעזרו לממש אותו.
