# LLM - מנוע החשיבה של הסוכן

אחרי שראינו את המבנה הכללי של Agent, אפשר להתמקד ברכיב המרכזי שמאפשר לו להבין שפה, להסיק מסקנות ולנסח תשובות: ה-LLM.

חשוב להבין את התפקיד שלו בצורה מדויקת. ה-LLM הוא רכיב חזק מאוד, אבל הוא לא כל המערכת. הוא לא הזיכרון, לא הכלים, לא מסד הנתונים ולא מנגנון האבטחה. הוא מנוע השפה והחשיבה שה-Agent מפעיל בתוך תהליך רחב יותר.

במערכת Agent, ה-LLM עוזר לתרגם בקשה אנושית למשמעות שהמערכת יכולה לעבוד איתה. המשתמש לא חייב לכתוב פקודה טכנית מדויקת או לבחור פעולה מתוך רשימה. הוא יכול לכתוב בקשה רגילה, לפעמים קצרה, לפעמים לא מדויקת, וה-LLM עוזר להבין למה הוא מתכוון.

לדוגמה, המשתמש יכול לכתוב:

```bash
Can you explain this code in simple words?
```

ה-LLM מבין שזו לא בקשה להריץ את הקוד, אלא להסביר אותו. הוא גם מבין שההסבר צריך להיות פשוט, ולא טכני מדי.

עם זאת, ה-LLM לא אמור לעשות הכול לבד. כאשר צריך מידע מדויק, נתון עדכני, גישה למסמך או פעולה במערכת חיצונית, ה-Agent צריך לחבר אותו לזיכרון, לכלים או למקור מידע מתאים.

במילים פשוטות: ה-LLM הוא מנוע ההבנה והניסוח של הסוכן, אבל ה-Agent הוא המערכת שמנהלת סביבו את ההקשר, הכלים, הזיכרון והפעולות.

## מה ה-LLM עושה

ה-LLM הוא הרכיב שמאפשר ל-Agent לעבוד עם שפה טבעית. הוא עוזר למערכת להבין מה המשתמש מבקש, גם כאשר הבקשה אינה מנוסחת כפקודה טכנית מדויקת.

בתוך Agent, ה-LLM יכול לעזור בכמה פעולות מרכזיות:

- להבין שפה טבעית.

- לזהות את כוונת המשתמש.

- לסווג את סוג הבקשה.

- לפרק משימה לתת-שלבים.

- לנסח תשובה ברורה.

- להסביר תוצאה שחזרה מכלי.

- להחליט, במקרים מסוימים, מה הצעד הבא.

לדוגמה, אם המשתמש שואל:

```bash
What does this document say about vector databases?
```

ה-LLM יכול להבין שהשאלה קשורה למסמך מסוים ולא לידע כללי. אבל הוא לא אמור להמציא את תוכן המסמך. ה-Agent צריך לשלוף את המידע הרלוונטי מהמסמך או ממאגר RAG, ורק אז ה-LLM ינסח תשובה לפי ה-context שקיבל.

בדוגמה אחרת, אם המשתמש שואל על נתון משתנה, כמו מחיר מניה או סטטוס משלוח, ה-LLM יכול להבין שצריך מקור חיצוני. אבל הנתון עצמו צריך להגיע מכלי מתאים, ולא מהידע הפנימי של המודל.

במילים פשוטות, הכוח של ה-LLM הוא לא בכך שהוא יודע הכול, אלא בכך שהוא יודע לעבוד עם שפה, להבין כוונה, ולחבר בין מידע לבין תשובה ברורה. בתוך Agent, זו יכולת קריטית, אבל היא צריכה לעבוד יחד עם זיכרון, כלים והנחיות.

## למה זה חשוב

החשיבות של ה-LLM בתוך Agent נובעת מכך שמשתמשים לא עובדים כמו תוכנה. הם לא תמיד יודעים איזה כלי צריך להפעיל, איזה מידע חסר, או איך לנסח את המשימה בצורה טכנית. הם פשוט כותבים את מה שהם צריכים בשפה טבעית.

לדוגמה, משתמש יכול לכתוב:

```bash
Can you check if this answer is based on the documents?
```

זו לא פקודה טכנית. המשתמש לא אמר למערכת איך לבדוק את זה, אבל ה-LLM יכול להבין שהכוונה היא לבדוק האם התשובה נשענת על מידע קיים ולא על ניחוש.

במקרה אחר, המשתמש יכול לכתוב:

```bash
This explanation is too complicated. Make it easier for beginners.
```

כאן אין צורך בכלי חיצוני. ה-LLM מבין שמדובר בשכתוב ובהורדת רמת המורכבות של ההסבר.

כלומר, ה-LLM מגשר בין השפה האנושית לבין פעולות שהתוכנה יכולה לבצע. הוא עוזר למערכת להבין מה המשתמש רוצה, ולא רק איזה טקסט הוא כתב.

עם זאת, ההבנה הזאת היא רק חלק מהמערכת. אחרי שה-LLM עוזר להבין את הבקשה, ה-Agent צריך להחליט האם לענות מיד, לשלוף מידע מהזיכרון, להפעיל כלי, לשאול שאלת הבהרה, או לעצור לפני פעולה רגישה.



## מה ה-Agent שולח ל-LLM

ה-LLM לא עובד בחלל ריק. בכל קריאה אליו, ה-Agent מחליט איזה מידע לשלוח לו כדי שיוכל להבין את המשימה ולייצר תשובה טובה יותר.

במקרה הפשוט ביותר, ה-Agent יכול לשלוח רק את בקשת המשתמש:

```bash
User: Explain what an AI Agent is.
```

אבל במערכת אמיתית, לרוב נשלחים למודל עוד פרטים:

- הנחיות מערכת.

- היסטוריית שיחה רלוונטית.

- מידע שנשלף ממסמכים או ממערכת RAG.

- רשימת כלים זמינים.

- תוצאות של פעולות קודמות.

לדוגמה, אם המשתמש שואל על תוכן של מסמך, ה-Agent לא צריך לשלוח למודל רק את השאלה. הוא צריך קודם לשלוף את הקטעים הרלוונטיים, ואז לשלוח למודל את השאלה יחד עם ה-context שנמצא.

במקרה של Agent עם Tools, ה-Agent יכול לשלוח למודל גם תיאור של הכלים הזמינים, למשל:

```python
Available tool:
get_stock_info(symbol) - returns current stock information for a ticker symbol.
```

כך ה-LLM יכול להבין שהכלי הזה רלוונטי כאשר המשתמש שואל על מידע שדורש נתוני שוק עדכניים.

לכן השאלה החשובה אינה רק “איזה מודל נבחר”, אלא גם “איזה מידע נשלח למודל”. אותו LLM יכול להחזיר תשובה חלשה אם הוא מקבל מעט מדי הקשר, ותשובה טובה בהרבה אם ה-Agent מספק לו את ההנחיות, המקורות, הכלים והתוצאות הנכונות.



## שימוש ביותר ממודל אחד

במערכת Agent לא חייבים להשתמש תמיד באותו LLM לכל סוגי המשימות. אפשר לבנות ארכיטקטורה שבה הסוכן משתמש ביותר ממודל אחד, וכל מודל מתאים לסוג אחר של פעולה.

לדוגמה, משימה מורכבת שדורשת ניתוח עמוק, תכנון, כתיבת קוד או קבלת החלטה רגישה יכולה לעבור למודל חזק יותר. לעומת זאת, משימה פשוטה כמו סיווג קצר, ניסוח בסיסי, חילוץ שדה מטקסט או בדיקה טכנית פשוטה יכולה לעבור למודל קטן, מהיר וזול יותר.

הגישה הזאת חשובה כי לא כל פעולה של Agent דורשת את אותה רמת יכולת. אם כל בקשה עוברת תמיד למודל החזק והיקר ביותר, המערכת עלולה להיות יקרה ואיטית יותר מהנדרש. מצד שני, אם כל הבקשות עוברות למודל פשוט מדי, המערכת עלולה להיכשל במשימות שדורשות הבנה עמוקה יותר.

אפשר לחשוב על זה כעל Routing בין מודלים:

```bash
Complex reasoning task → Strong model
Simple classification task → Smaller model
Code analysis task → Code-focused model
Fast formatting task → Lightweight model
```

במקרה כזה, ה-Agent לא רק בוחר אם להשתמש בכלי או בזיכרון, אלא גם בוחר באיזה מודל להשתמש עבור השלב הנוכחי. זו החלטה ארכיטקטונית שמשפיעה על איכות, עלות, מהירות ואמינות.

חשוב לזכור שגם כאן צריך גבולות ברורים. ככל שמשלבים יותר מודלים, כך צריך להבין מה התפקיד של כל מודל, אילו משימות מתאימות לו, ואיך בודקים שהתוצאה שלו מספיק טובה. שימוש בכמה מודלים יכול לשפר את המערכת, אבל רק אם החלוקה ביניהם מוגדרת בצורה ברורה.

## דוגמה פשוטה

נניח שהמשתמש שואל:

```bash
What is the current stock price of Apple?
```

ה-LLM יכול להבין כמה דברים מתוך השאלה: המשתמש שואל על חברת Apple, הכוונה היא כנראה למניה של Apple, והסימול הרלוונטי הוא בדרך כלל AAPL. הוא גם יכול להבין שמדובר בנתון עדכני, ולכן לא נכון לענות רק מתוך הידע הפנימי של המודל.

במקרה כזה, התפקיד של ה-LLM הוא לא לדעת את מחיר המניה בעצמו, אלא להבין שצריך להשתמש בכלי מתאים.

הזרימה יכולה להיראות כך:

הזרימה יכולה להיראות כך:

```bash
User asks about Apple stock price
        ↓
LLM understands this requires current data
        ↓
Agent uses stock data tool
        ↓
Tool returns the current price
        ↓
LLM explains the result clearly
```

הדוגמה הזאת מראה את ההפרדה החשובה בין הבנה לבין מקור מידע. ה-LLM עוזר להבין את הבקשה ולנסח את התשובה, אבל הנתון עצמו מגיע מהכלי.

אותו עיקרון נכון גם בשאלות על מסמכים, מערכות פנימיות או נתונים משתנים. בתוך Agent, ה-LLM הוא לא תמיד מקור התשובה. לפעמים הוא המוח שמבין מה צריך לעשות, והכלים או הזיכרון הם אלה שמביאים את המידע שעליו התשובה מתבססת.

## טעויות נפוצות

**הטעות הראשונה** היא לחשוב שה-LLM הוא מקור אמת לכל דבר. בפועל, מודל שפה טוב מאוד בהבנה, ניסוח והסקה, אבל הוא לא תחליף למקור מידע אמין כאשר צריך נתון מדויק, עדכני או פרטי.

**הטעות השנייה** היא לתת ל-LLM יותר מדי חופש פעולה בלי גבולות ברורים. ככל שהסוכן יכול להפעיל יותר כלים או לבצע פעולות משמעותיות יותר, כך חשוב להגדיר מה מותר לו לעשות, מה אסור לו לעשות, ומתי נדרש אישור משתמש.

**הטעות השלישית** היא לא לבדוק את הפלט. תשובה שמנוסחת היטב אינה בהכרח תשובה נכונה. במערכת טובה צריך לבדוק האם התשובה מבוססת על context מתאים, האם הכלי החזיר תוצאה תקינה, והאם אין סתירה בין הנתונים לבין ההסבר.

**הטעות הרביעית** היא לבלבל בין ניסוח תשובה לבין אימות נתונים. ה-LLM יכול להסביר, לפשט, לסכם ולארגן מידע, אבל כאשר צריך לאמת נתון, צריך להשתמש במקור מתאים: מסמך, API, מסד נתונים, כלי חישוב או מערכת חיצונית.

לכן בבניית Agent חשוב לזכור שה-LLM הוא רכיב מרכזי, אבל לא רכיב יחיד. הוא צריך לעבוד יחד עם זיכרון, כלים, הנחיות, בדיקות וגבולות פעולה ברורים.

זו הבחנה חשובה מאוד בבניית Agents. ה-LLM יכול לעזור למערכת להבין מה צריך לעשות, אבל הוא לא תמיד המקום שממנו צריכה להגיע האמת העובדתית.
